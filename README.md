# Система оформления договора страхования жизни

Тестовое задание BackEnd. Два сервиса: `insurance-service` (страхование) и `registry-emulator` (эмулятор Государственного страхового реестра), Keycloak, БД PostgreSQL (у каждого сервиса своя).

## Модель данных

Заявка (`application`) и договор (`contract`) - это разные сущности с ассоциацией (внешний ключ, а не просто колонка). 

В договоре хранится снимок условий на момент выпуска, а не ссылка на заявку целиком. Заявку можно поменять, а договор должен быть неизменным.

Предметная область упрощена: страхователь и застрахованный - это одно лицо, выгодоприобретателя нет, валюта условная и в модели не хранится, тарификация условная (коэффициенты вынесены в конфигурацию).

- Деньги - `BigDecimal`/`numeric(15,2)`,
- отметки времени - `Instant`/`timestamptz`, 
- идентификаторы - UUID, присваиваю при вставке в БД, а не в конструкторе.

Номер договора (`LI-2026-000042`) - генерируемая колонка БД на основе последовательности; нумерация сквозная, а не годовая.

## Защита от повторных операций

`POST /api/v1/applications/{applicationId}/contract` идемпотентен по `applicationId`, а не по отдельному ключу идемпотентности: 
- первый вызов - 201 с новым договором, 
- любой следующий - 200 с тем же самым. 

Гарантирует это уникальный индекс на `contract.application_id` в схеме БД, поэтому не зависит от кода приложения.

Регистрация договора в реестре: идемпотентность по **идентификатору договора** (UUID), а не по номеру, т.к. номер выдаётся последовательностью и после пересоздания БД сервиса может повториться, а UUID всегда уникален.

## Подход к конкурентным запросам

Выпуск договора защищён тремя независимыми уровнями: 
- уникальный индекс в схеме (последняя гарантия), 
- пессимистическая блокировка строки заявки (делает поведение конкурентных запросов детерминированным) и 
- быстрая проверка «договор уже есть» до открытия транзакции (повторные запросы блокировку вообще не берут).

Обязательный тест конкурентности выпускает один договор восемью параллельными запросами и только один получает 201, семь остальных получают 200 с тем же договором.

Фоновый захват задач на регистрацию использует `SELECT ... FOR NO KEY UPDATE ... SKIP LOCKED` и берёт задачи по одной, поэтому если экземпляров сервиса несколько, то они не могут взять одну и ту же задачу.

## Интеграция с реестром

Клиент реестра - декларативный (`@HttpExchange`) поверх `RestClient`. Принудительно установил HTTP/1.1, т.к. WireMock в тестах на это предложение рвал соединение.

Задача на регистрацию создаётся **в одной транзакции с договором**, поэтому одного без другого не бывает. 

После запроса на выпуск, отправка заявки выполняется отдельным фоновым планировщиком: клиент получает ответ на выпуск сразу, не дожидаясь ответа от реестра.

## Обработка недоступности реестра

Планировщик забирает задачу **в аренду**: он сдвигает время следующей попытки на срок аренды и увеличивает счётчик до самого вызова реестра - если процесс упадёт посреди вызова, задача просто станет доступной для повторного захвата, когда аренда истечёт. 

Отдельный статус «в работе» не нужен, состояние целиком лежит в БД.

При неудаче выставил экспоненциальную задержку с потолком перед следующей попыткой. **Предела числа попыток нет**: недоступность реестра не приводит к окончательному отказу - регистрация продолжится, когда реестр оживет.

## Классификация ошибок для повторной обработки

Категорию определяет код ответа реестра:
- любой 2xx - успех;
- 5xx, 429, любая ошибка ввода-вывода - повторяемая ошибка, задача остаётся в очереди;
- 4xx (кроме 429) с распознанным кодом бизнес-отказа в теле (422 `REGISTRATION_REJECTED`) становится окончательным отказом по существу, а задача помечается `REJECTED` и больше автоматически не обрабатывается;
- остальные 4xx (неверный адрес, протухший доступ и т.п.) - окончательная техническая ошибка, задача помечается `FAILED`;
- всё нераспознанное трактуется как повторяемая ошибка, чтобы неизвестное исключение не роняло планировщик молча.

## Статусы

- `PENDING` - ждёт отправки или следующей попытки, дальше сам возьмёт фоновый процесс.
- `REGISTERED` - договор зарегистрирован, `registryRecordId` заполнен.
- `REJECTED` - реестр отказал по существу. Тупиковое состояние, автоматика его больше не трогает, обратно вернуть нельзя.
- `FAILED` - окончательная ошибка по нашей вине (неверный адрес или протухший доступ). Не означает, что в реестре записи нет: договор мог зарегистрироваться, а сорваться могло только чтение ответа. Сотрудник может вручную вернуть задачу в очередь (`POST /api/v1/contracts/{contractId}/registration/retry`), счётчик попыток при этом не обнуляется.

## Основные технические решения

- Многомодульный проект, **без общего модуля с DTO** между сервисами, с дублированием контрактов для поддержания границы внешней системы. Поэтому расхождение контрактов ловит только ручной прогон на стенде, а не тесты.
- Пакеты осознанно распределены по предметной сущности, не по техническому слою.
- Работа велась последовательно в одиночку, поэтому ветки и PR не использовались, т.к. не нужды в координации нескольких участников.
- Добавлен каталог версий `libs.versions.toml`, чтобы `insurance-service` и `registry-emulator` использовали одинаковые версии зависимостей.
- Добавлен @NullMarked в каждом package-info.java - такая же система пометок null, которая используется в Spring начиная с 7 версии.
- Пакеты `contracts` и `registrations` внутри `insurance-service` знают друг о друге в обе стороны: договор и задача на его регистрацию создаются в одной транзакции, поэтому и код выпуска договора обращается к регистрации, и код отправки в реестр - к договору. Разделять их слоем ради формальной однонаправленности не стал: это спрятало бы связь, а не убрало.
- Liquibase для схемы, Testcontainers с PostgreSQL и WireMock (заглушка реестра в тестах).
- Каждый запрос получает `X-Request-Id` (свой или сгенерированный) - виден в каждой связанной строке лога, в т.ч. и в фоновой попытке регистрации, которую позже выполнит планировщик уже после запроса.
- Ошибки API - единый формат `ProblemDetail` с полем `code`, включая отказы на уровне фильтров (401 без токена, 403 до диспетчера запросов).
- Для удобства проверки сценариев используется устаревший password grant: он позволяет ввести логин и пароль прямо на странице Swagger.

## Порядок запуска приложения

- `docker compose build`
- `docker compose up` 
  - или одной командой `docker compose up -d --build --wait`
- открыть http://localhost:8081/swagger-ui/index.html
- открыть окно авторизации и ввести требуемого пользователя
  - `customer1` пароль `customer1`
  - `customer2` пароль `customer2`
  - `underwriter1` пароль `underwriter1`

После авторизации выполнить сценарии.

### Сценарий пользователя

1. Авторизоваться `customer1` / `customer1`.
2. `POST /api/v1/applications` → Try it out → тело:
   ```json
   {
     "insuredFullName": "Иван Петров",
     "insuredBirthDate": "1990-05-15",
     "insuredDocumentNumber": "AB1234567",
     "coverageAmount": 1000000,
     "termYears": 10
   }
   ```
3. Execute - 201, из ответа взять `applicationId`.
4. `GET /api/v1/applications/{applicationId}` с этим `applicationId` - своя заявка видна, статус `SUBMITTED`.

### Сценарий работника

1. Открыть окно авторизации, Logout, залогиниться `underwriter1` / `underwriter1`.
2. `GET /api/v1/applications` - заявка клиента видна в общем списке.
3. `POST /api/v1/applications/{applicationId}/approve` с `applicationId` из шага 3 сценария пользователя - статус становится `APPROVED`.
4. `POST /api/v1/applications/{applicationId}/contract` - 201, тело содержит `contractId` (другой UUID, не заявки) и `registration.status = PENDING`.
5. Подождать пару секунд - фоновый планировщик успевает сработать.
6. `GET /api/v1/contracts/{contractId}` с `contractId` из шага 4 - `registration.status` стал `REGISTERED`, `registryRecordId` заполнен.

### Проверка недоступности реестра

Нужна свежая заявка - уже выпущенный договор из основного сценария не подойдёт (либо не одобрится повторно, либо выпустится ещё раз тем же самым, уже зарегистрированным договором).

1. В терминале: `docker compose stop registry-emulator`.
2. Заново пройти шаг 2 сценария пользователя (создать новую заявку от `customer1`).
3. Logout, залогиниться `underwriter1` / `underwriter1`, пройти шаги 3-4 сценария работника (одобрить, выпустить) - получить новый договор, `registration.status = PENDING`.
4. Несколько раз `GET /api/v1/contracts/{contractId}` с паузой - `attempts` растёт, статус остаётся `PENDING`.
5. `docker compose start registry-emulator`.
6. Через несколько секунд `GET` снова - статус сам станет `REGISTERED`, без повторных действий.

### Проверка перезапуска сервиса

Тоже нужна свежая заявка - по той же причине.

1. `docker compose stop registry-emulator`.
2. Заново пройти шаг 2 сценария пользователя (создать новую заявку от `customer1`).
3. Logout, залогиниться `underwriter1` / `underwriter1`, пройти шаги 3-4 сценария работника - получить новый договор, `PENDING`.
4. `docker compose up -d --force-recreate insurance-service` - пересоздаёт контейнер целиком (новый container ID), а не просто перезапускает процесс в старом, ближе к замене пода в Kubernetes.
5. `docker compose start registry-emulator`.
6. Подождать, `GET /api/v1/contracts/{contractId}` - `REGISTERED`. Договор довёл до конца уже новый экземпляр сервиса, а не тот, что его создавал.

### Переключение режима эмулятора реестра

`registry-emulator` воспроизводит четыре сценария из задания (и `SLOW` сверху), режим переключается напрямую HTTP-вызовом - у эмулятора нет Swagger UI, это не наш сервис, а стенд-двойник внешней системы.

- `GET http://localhost:8082/api/v1/emulator/mode` - текущий режим.
- `POST http://localhost:8082/api/v1/emulator/mode` с телом `{"mode": "..."}` - переключить.

```bash
# успешная регистрация (режим по умолчанию)
curl -X POST http://localhost:8082/api/v1/emulator/mode -H "Content-Type: application/json" -d '{"mode":"SUCCESS"}'

# бизнес-отказ - договор попадёт в REJECTED
curl -X POST http://localhost:8082/api/v1/emulator/mode -H "Content-Type: application/json" -d '{"mode":"BUSINESS_ERROR"}'

# техническая ошибка (500) - повторяемая, договор останется PENDING
curl -X POST http://localhost:8082/api/v1/emulator/mode -H "Content-Type: application/json" -d '{"mode":"TECHNICAL_ERROR"}'

# недоступность (503) - то же самое, что docker compose stop registry-emulator
curl -X POST http://localhost:8082/api/v1/emulator/mode -H "Content-Type: application/json" -d '{"mode":"UNAVAILABLE"}'

# искусственная задержка ответа, по умолчанию 10 секунд
curl -X POST http://localhost:8082/api/v1/emulator/mode -H "Content-Type: application/json" -d '{"mode":"SLOW","slowDelaySeconds":5}'
```

Режим действует сразу для всех последующих вызовов. После рестарта снова `SUCCESS`.
